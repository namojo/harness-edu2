# 하네스 개념 — 원본 정본과 집필 규칙

## 왜 정본을 고정하는가

학습자는 교재를 읽고 나서 `github.com/revfactory/harness`를 보러 간다. 거기서 패턴 이름이나 단계 수가 다르면, 학습자는 자기가 뭘 잘못 읽었는지 알 수 없다. 교재의 신뢰는 원본과의 일치에서 나온다.

그래서 이 스킬의 규칙은 하나로 요약된다: **개념은 창작하지 않고 인용한다.** 창작하는 것은 설명 방식과 예시뿐이다.

## 개념 페이지의 3부 구성

순서를 바꾸지 않는다. 이 순서는 "왜 필요한가 → 어떻게 만들어지나 → 어떤 모양이 있나"이며, 마지막이 실습으로 이어진다.

### 1부 · 하네스 엔지니어링 (왜)

전달할 것 셋:

1. **일회성 프롬프트 → 반복 가능한 시스템.** 프롬프트를 잘 쓰는 것과 일하는 방식을 설계하는 것의 차이. 프롬프트는 결과 한 번을 좋게 하고, 하네스는 다음 사람과 다음 달의 결과까지 좋게 한다.
2. **에이전트(누가) × 스킬(어떻게) 분리.** 이 교재 전체를 관통하는 한 문장이다. 역할과 절차를 한 덩어리로 쓰면 재사용이 안 된다.
3. **하네스 진화 메커니즘.** 하네스는 고정물이 아니다. 실제로 써 보고 초기 구성과 최종 구성의 델타를 되먹여 다음 세대를 더 좋게 만든다. 원본의 도식(초기 하네스 → 실 사용 → 출시 하네스 → 팩토리 되먹임)을 인용한다.

**하지 말 것:** "AI에게 일을 맡기는 3단계 성숙도 모델" 같은 원본에 없는 프레임워크를 만들어 넣는 것. 그럴듯해 보여도 원본에 없으면 학습자가 확인할 곳이 없다.

### 2부 · 메타스킬 6단계 (어떻게 만들어지나)

`도메인 분석 → 아키텍처 설계 → 에이전트 정의 → 스킬 생성 → 오케스트레이션 → 검증`

각 단계마다 **한 줄 설명 + "이 단계에서 결정되는 것"** 을 붙인다. 학습자가 실습에서 하네스를 돌릴 때 화면에서 이 6단계가 지나가는 것을 알아볼 수 있게 하는 것이 목적이다.

> 원본 SKILL.md는 Phase 0(현황 감사)과 Phase 7(진화)까지 포함한다. 교재는 **6단계로 가르치고**, Phase 0·7은 "이미 만든 하네스를 고칠 때 앞뒤로 붙는 단계"로 각주 처리한다. 이유: 첫 구성 경험에는 6단계가 실제로 보이는 전부다. 이 축약은 의도된 것이므로 각주에 명시한다.

### 3부 · 6가지 아키텍처 패턴 (어떤 모양)

**6장의 카드가 동일한 4슬롯을 갖는다.** 형식이 갈리면 비교가 불가능하다.

| 패턴 | 흐름 (한 줄 도식) | 한 줄 정의 | 이럴 때 고른다 | 교재 등장 |
|---|---|---|---|---|
| 파이프라인 | `A → B → C` | 앞 단계 결과가 다음 단계 입력 | 순서를 바꿀 수 없는 일 | 실습 3 |
| 팬아웃 / 팬인 | `분배 → A·B·C → 통합` | 독립 관점을 동시에 모아 하나로 합침 | 관점이 서로를 기다릴 필요 없는 조사 | 실습 2 |
| 전문가 풀 | `상황 → 필요한 전문가만` | 상황에 맞는 담당자를 골라 호출 | 매번 필요한 전문성이 다른 일 | 실습 1 확장 |
| 생성-검증 | `생성 → 검증 → 수정` | 만드는 쪽과 검사하는 쪽을 분리 | 품질 기준이 명확한 산출물 | 실습 2·3 |
| 감독자 | `중앙 → 동적 분배` | 중앙 담당자가 상태를 보며 일을 나눔 | 일의 양·순서를 미리 못 정하는 경우 | 개념만 |
| 계층적 위임 | `상위 → 하위 → 하위` | 상위 담당자가 하위에게 재귀적으로 위임 | 큰 일을 계속 쪼개야 하는 경우 | 개념만 |

> 원본은 8패턴(+ 조건부 토론, 단계별 팀 재구성)을 제공한다. 교재는 6개만 가르치고 나머지 2개는 "심화 2종"으로 이름과 한 줄 정의만 각주에 남긴다. 8개를 15분에 넣으면 6개도 못 남는다.

**"교재 등장" 열이 이 표의 핵심이다.** 개념이 실습으로 착지하지 않으면 학습자는 6개를 다 잊는다. `감독자`·`계층적 위임`처럼 실습에 없는 패턴은 "이런 것도 있습니다" 수준으로 짧게 둔다 — 분량을 균등 배분하려는 충동을 누른다.

### 3부 마무리 · 패턴 선택 3질문

패턴 표보다 이 3질문이 실무에서 더 쓰인다. 정의를 외우는 게 아니라 판단하는 것이 목표다.

1. **앞 단계 결과가 다음 단계에 꼭 필요한가?** → 예: 파이프라인
2. **독립된 관점을 동시에 모을 수 있는가?** → 예: 팬아웃 / 팬인
3. **만든 사람이 아닌 다른 눈이 검사해야 하는가?** → 예: 생성-검증

세 질문에 다 "예"면 세 패턴을 겹쳐 쓴다 — 실습 2·3이 정확히 그 경우다. 패턴은 배타적 선택지가 아니라는 점을 반드시 한 문장으로 밝힌다. 이것을 빼면 학습자는 "내 일은 어느 하나에 속하나"에서 막힌다.

## 집필 규칙

1. **각 개념 블록은 실습 링크로 닫는다.** `→ 실습 2에서 직접 확인합니다` 형태.
2. **출처는 문서 단위로 표기한다.** 패턴표·6단계처럼 원본에서 온 구조물에는 `출처: revfactory/harness · agent-design-patterns.md` 를 붙인다. 문장마다 붙이면 읽기가 망가진다.
3. **비전공자 예시는 사무실 언어로 든다.** "CI 파이프라인"이 아니라 "품의 결재선", "코드 리뷰"가 아니라 "타 부서 검토".
4. **`_workspace/02_curator_sources.md`에 주장 → 출처 매핑을 남긴다.** 나중에 원본이 갱신되면 어느 문장을 고쳐야 하는지 이 표로 찾는다.
5. **도식은 직접 그리지 않고 명세만 쓴다.** `_workspace/02_curator_diagrams.md`에 "무엇과 무엇의 어떤 관계를 보여야 하는가"를 적고, 구현은 `web-builder`에게 넘긴다.

## 자주 나는 결함

| 결함 | 왜 생기나 | 어떻게 막나 |
|---|---|---|
| 패턴 이름이 실습 페이지와 다름 | 두 작성자가 각자 번역 | 이 문서의 표기를 유일 정본으로 삼고 `practice-designer`에게 통보 |
| 6패턴 분량이 균등 | 대칭을 만들려는 충동 | "교재 등장" 열 기준으로 차등 배분 |
| 원본에 없는 프레임워크 등장 | 설명을 매끄럽게 하려다 창작 | `02_curator_sources.md`에 출처를 못 적는 문장은 삭제 |
| 개념이 실습보다 길어짐 | 개념은 쓰기 쉽고 실습은 어렵다 | 4,000자 상한을 먼저 재고 초과분부터 자른다 |
| 8패턴을 다 설명 | 원본 충실성과 교육 효과를 혼동 | 6 + 각주 2 구조를 지킨다 |
