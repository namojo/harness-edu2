# 실습 페이지 집필

## 이 페이지가 성공하는 조건

실습 페이지는 읽히는 글이 아니다. **학습자가 Claude Code 창을 옆에 띄워 놓고 번갈아 보는 작업 지시서**다. 성공 조건은 셋이다:

1. 프롬프트를 **복사해서 붙여넣으면 그대로 돌아간다**
2. 결과가 나왔을 때 **맞게 나온 건지 학습자 혼자 판정할 수 있다**
3. 막혔을 때 **페이지 안에서 답을 찾는다** (강사를 부르지 않는다)

이 셋에 기여하지 않는 문장은 분량만 차지한다. 배경 설명·업계 동향·하네스 예찬은 개념 페이지의 일이다.

## 9블록 골격 — 세 페이지가 동일하게 쓴다

순서를 바꾸지 않는다. 학습자는 실습 1에서 익힌 읽기 순서를 2·3에서 반복하며, 순서가 달라지면 매번 다시 적응해야 한다.

| # | 블록 | 목적 | 분량 기준 |
|---|---|---|---|
| 1 | **상단 3줄** | eyebrow(`실습 N · N분`) / h1 / 학습 목표 한 문장 | 고정 |
| 2 | **준비물** | 이 실습에 필요한 파일과 받는 방법 두 경로 | 표 또는 2행 |
| 3 | **이번 실습에서 확인할 것** | 3~5개 항목. 이 실습이 무엇을 증명하는지 | 카드 3~5장 |
| 4 | **브리프** | 복사 버튼이 붙은 프롬프트 원문 + 브리프 4요소 해설 | 원문 + 300자 |
| 5 | **예상 팀** | 역할 · 책임 · 전달물 표 + 패턴 도식 | 표 + 도식 1 |
| 6 | **예상 산출물** | 최종 결과물의 형태 | 300~500자 |
| 7 | **검토 체크리스트** | 학습자가 O/X를 매기는 항목 5~8개 | 체크박스 |
| 8 | **이럴 때는** | 트러블슈팅 3~5개 | 각 2~3줄 |
| 9 | **다음 단계** | 페이저 + 다음 실습이 이걸 어떻게 쓰는지 | 2줄 |

블록 이름도 세 페이지에서 동일하게 쓴다. "예상 팀"을 한 페이지에서만 "팀 구성"이라 쓰면 학습자는 다른 것인 줄 안다.

**준비물이 2번인 것은 의도적이다.** 학습자가 파일을 찾는 시점은 실습을 시작하는 순간이고, 그때 눈이 가는 곳은 페이지 상단이다. 준비물을 아래에 두면 브리프를 먼저 복사해 실행한 뒤에야 입력 파일이 없다는 것을 알게 된다.

## 블록별 집필 규칙

### 2. 준비물 — 두 경로를 나란히 준다

교실에서 실제로 벌어지는 일: 사전 준비를 마친 학습자는 `clone`한 폴더에서 파일을 찾고, 지각한 학습자와 노트북을 바꿔 온 학습자는 그 폴더가 없다. **한 경로만 제공하면 반드시 절반이 막힌다.**

| 경로 | 내용 |
|---|---|
| A. 실습 저장소를 받은 경우 | `harness-edu/workshop/practice-N-.../` 폴더를 Claude Code에서 연다 |
| B. 개별 다운로드 | 파일별 다운로드 링크 (파일명 · 용도 한 줄 · 용량) |

**실습 1·2는 입력 파일이 없다.** 준비물 블록을 없애지 말고, "입력 파일 없음 — 브리프 한 편이 전부입니다. Claude Code가 실행되는지만 확인하세요"로 채운다. 블록을 지우면 세 페이지의 골격이 갈리고, 학습자는 실습 3에서 처음 보는 블록을 만난다.

**실습 3의 준비물에는 실습 2 의존성 고지가 함께 들어간다** (아래 §9 참조).

파일 목록·다운로드 URL·용량은 `practice-assets` 스킬과 `_workspace/07_assets_manifest.md`가 정본이다. 여기서 URL을 직접 만들지 않는다 — 브랜치명·경로를 추측하면 전부 404가 된다.

### 4. 브리프 — 원문을 한 글자도 바꾸지 않는다

브리프 원문은 `references/practice-briefs.md`가 **유일한 정본**이다. 표현을 다듬고 싶어도 그대로 둔다. 학습자가 슬라이드와 웹을 번갈아 보다 다른 문장을 발견하면 어느 쪽이 맞는지 알 수 없다. 다듬을 것이 있으면 프롬프트 **밖의 해설**로 붙인다.

원문에는 이중 공백·en dash 같은 함정이 있다. 반드시 `references/practice-briefs.md`의 §보존 함정을 읽고 작업한다.

브리프 해설은 **4요소 형태**로 쓴다. 학습자가 자기 업무로 브리프를 다시 쓸 때 쓰는 틀이다:

| 요소 | 실습 1의 예 |
|---|---|
| 목표 (무엇을 받고 싶은가) | 1주치 콘텐츠 기획안 |
| 대상 (누구를 위한 것인가) | 20대 직장인 |
| 역할 (누가 필요한가) | 트렌드 조사 · 대본 기획 · SEO · 썸네일 |
| 기준 (무엇을 지켜야 하는가) | 주장마다 근거 출처 |

플레이스홀더(`[브랜드/주제]`, `[20대 직장인]`)는 **시각적으로 구분하되 복사되는 텍스트에는 태그가 섞이지 않게** 한다. 학습자가 붙여넣은 프롬프트에 `<span>`이 들어가면 첫 동작부터 실패한다.

### 5. 예상 팀 — 정답이 아니라 기준선이다

하네스는 실행할 때마다 다른 팀을 만든다. 그래서 "이렇게 나와야 한다"로 쓰면 안 된다. 학습자 결과가 예시와 달라서 실패했다고 느끼게 만드는 것이 이 페이지의 최악의 실패다.

대신 **네 가지가 결정되었으면 성공**으로 쓴다:

1. **역할 경계** — 누가 무엇까지 하는지가 겹치지 않게 갈렸는가
2. **전달 관계** — 누가 누구에게 무엇을 넘기는지가 정해졌는가
3. **최종 형식** — 산출물의 형태가 명시되었는가
4. **별도 리뷰** — 만든 사람이 아닌 눈이 검사하는가

표는 `역할 | 책임 | 전달물` 3열로 쓴다. "능력"이나 "특성" 열은 만들지 않는다 — 학습자가 자기 결과와 대조할 수 없다.

패턴 도식은 `harness-concept-source`가 확정한 패턴 이름을 그대로 쓴다. 개념 페이지와 이름이 갈리면 학습자는 15분 전에 배운 것을 못 알아본다.

### 7. 검토 체크리스트 — 혼자 O/X를 매길 수 있어야 한다

**금지 표현:** 적절한가 · 충분한가 · 품질이 좋은가 · 잘 되었는가 · 논리적인가

이런 항목은 학습자가 판정할 수 없어서 전부 O가 되고, 체크리스트가 무의미해진다.

**쓰는 형태:** 눈으로 세거나 있는지 없는지 확인할 수 있는 문장.

| 나쁨 | 좋음 |
|---|---|
| 근거가 충분한가 | 외부 주장마다 출처가 붙어 있는가 (붙지 않은 문장을 세어 보세요) |
| 전략이 명확한가 | 1페이지 요약에 "무엇을 하지 않을 것인가"가 적혀 있는가 |
| 우선순위가 적절한가 | 우선순위 표에 판단 근거 열이 있는가 |
| 팀 구성이 좋은가 | 두 에이전트의 책임이 겹치는 곳이 있는가 |
| PPT 품질이 높은가 | 3장의 본문 폰트 크기가 서로 같은가 |

체크리스트 앞에 **"몇 개 이상이면 통과"** 기준을 준다. 기준 없이 항목만 주면 학습자는 하나만 X여도 실패했다고 판단해 다음으로 넘어가지 않는다.

### 8. 이럴 때는 — 실제로 나는 것만 쓴다

발생 빈도 순으로. 상상해서 채우지 않는다. 세 페이지 공통으로 실제로 자주 나는 것:

| 증상 | 원인 | 대응 |
|---|---|---|
| 하네스가 트리거되지 않고 그냥 답만 한다 | 플러그인 미설치, 또는 브리프에 "하네스를 구성해줘"가 없다 | 설치가이드 확인 → 브리프 첫 줄 확인 |
| 팀이 8명 넘게 만들어진다 | 브리프의 역할 나열이 너무 세분화 | 역할을 묶어 다시 요청 |
| 산출물에 출처가 없다 | 브리프의 기준 문장이 약함 | "모든 외부 주장에 출처" 문장을 다시 강조해 재실행 |
| 실행이 오래 걸려 시간이 부족하다 | 조사 범위 무제한 | 조사 범위·개수 상한을 브리프에 추가 |
| 결과가 매번 다르다 | 정상 동작 | 하네스는 팀 구조를 만들고, 그 구조가 같으면 성공 |

실습별 고유 증상은 각 페이지의 references 절에서 확인한다.

### 9. 다음 단계 — 다음 실습이 이걸 어떻게 쓰는지 쓴다

`실습 1 → 2 → 3`은 난이도 순서가 아니라 **한 팀이 성장하는 세 단계**다: 팀을 만든다 → 구조를 고른다 → 산출물을 다듬는다. 이 연결을 각 페이지 마지막에 한 줄로 남긴다.

**실습 3은 실습 2의 산출물에 의존한다.** 이 사실을 실습 3의 **준비물 블록(2번)** 에 명시하고, 실습 2를 건너뛴 경우의 우회 경로(`example-strategy.md`)를 같은 블록에 둔다. 의존성만 써 놓고 대비책이 없으면 실습 3에서 교실 절반이 멈춘다.

그래서 실습 2의 다음 단계 블록에는 **"결과를 파일로 저장하세요"** 를 반드시 넣는다. 저장 안내가 없으면 실습 3에서 다시 만들어야 하고, 40분이 30분이 된다.

## 실습별 상세

각 실습의 브리프 원문·미션·예상 팀·산출물·고유 트러블슈팅은 아래를 읽는다:

- **브리프 원문 3편과 보존 함정** → `references/practice-briefs.md` (집필 전 반드시)
- **실습별 미션·팀·산출물·검토 항목** → `references/practice-specs.md`

## 데이터 안전 원칙

실제 고객정보·계약·인사·미공개 전략을 실습에 넣지 않는다. 공개 자료 또는 교육용 가상 데이터로 팀 구조를 먼저 검증한다.

이 원칙은 **실습 1에서 한 번 명시하고, 실습 2·3은 링크로 참조한다.** 세 페이지에 반복하면 학습자는 세 번째부터 읽지 않는다.

## 자주 나는 결함

| 결함 | 왜 생기나 | 어떻게 막나 |
|---|---|---|
| 프롬프트가 원문과 다름 | 이중 공백·en dash를 "오타"로 판단해 교정 | `references/practice-briefs.md`에서 복사, diff로 검증 |
| 판정 불가능한 체크리스트 | 쓰기 쉬운 표현이 판정 불가능한 표현이다 | 금지 표현 목록으로 자기 검사 |
| 예상 팀이 정답처럼 읽힘 | "예상"이라고 써 놓고 본문은 단정형 | 표 위에 "결정된 네 가지" 프레임을 먼저 둔다 |
| 실습 3에서 학습자 절반이 멈춤 | 실습 2 의존성만 명시하고 우회로 없음 | 예시 전략보고서를 자산으로 확보 |
| 페이지가 길어져 실행 시간이 줄어듦 | 트러블슈팅을 자세히 쓰다가 | 실습 페이지 본문 상한(2,000~3,000자) 준수 |
| 세 페이지 골격이 갈림 | 한 페이지만 개선 | 골격 변경은 세 페이지 동시에, `edu-architect` 승인 후 |
| 실습 1·2에 준비물 블록이 없음 | 입력 파일이 없으니 불필요하다고 판단 | "입력 파일 없음"으로 채운다 — 골격 일관성이 목적 |
| 다운로드 링크가 404 | 페이지에서 URL을 직접 조립 | `07_assets_manifest.md`의 URL을 그대로 쓴다 |
| 준비물을 페이지 하단에 둠 | 논리적 순서(개요→준비)를 따르려다 | 2번 위치 고정 — 파일이 없다는 것을 실행 전에 알아야 한다 |
